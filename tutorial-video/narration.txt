01. Complete setup and user guide
Welcome to the complete S I T setup and user guide. S I T means Smart Interactive Transcriber. It keeps recordings, speaker-labelled transcripts, and structured meeting analysis together in one local library. This guide uses the current zero point one point zero alpha release on Arch Linux. We will install the application, configure its managed SSH connections, record and upload audio, generate a transcript with remote Spark services, review speakers, create AI analysis, and manage the library. The model services themselves are outside this guide. Working remote endpoints are assumed, and this demonstration will not use the local transcription fallback.

02. Architecture and supported platforms
S I T has a FastAPI backend and the same web interface in a normal browser or a native Tauri window. On supported Linux audio systems, the recorder captures the microphone and the selected output monitor as separate channels. Each channel is transcribed independently, which protects clean system audio from room echo. Remote speech recognition and speaker recognition use Spark-compatible services. AI analysis uses a separate OpenAI-compatible endpoint. The application is verified end to end on Arch Linux with PipeWire Pulse or PulseAudio. Fedora, Ubuntu, Debian, and WSL two are documented, but not yet verified to the same level. WSL users should expect recording limitations and can always use file upload. Native Windows and macOS are not currently supported.

03. Install system dependencies
Start with system packages. On Arch Linux, install Git, curl, Python, uv, FFmpeg, and libpulse. Libpulse supplies the pactl client used to discover microphones, outputs, and monitor sources. Keep the PipeWire Pulse or PulseAudio server already provided by your desktop; do not replace it for S I T. If you only want the browser interface, the first command is enough. For the native window, also install the compiler toolchain, WebKit GTK, OpenSSL, the application indicator and SVG libraries, xdotool, and rustup. Then select the stable Rust toolchain. Fedora and Ubuntu use equivalent packages listed in the project readme. Use Python three point twelve when possible, or three point eleven. Newer rolling-release Python versions may not have every machine-learning wheel available.

04. Checkout and Python environment
Clone the repository, enter the checkout, and create a dedicated Python three point twelve environment named dot venv. Install requirements dot txt into that environment. This is the recommended remote-processing profile and keeps the environment small. It includes the application and the CPU ONNX transcription package, but this tutorial will use the configured remote services and will not demonstrate local fallback processing. The optional local Pyannote installation is intentionally omitted. Installing from the private repository requires GitHub access. The first model download, if local processing is ever enabled later, also requires network access and additional disk space. Keep the checkout after installation because the desktop launcher points to absolute paths inside it.

05. Launch in browser or desktop window
For the browser version, run the transcriber module and open the local address shown here. The backend remains active until you press Control C. For the native window, build the Tauri release binary and run the desktop installer. The installer needs no sudo access. It creates a launcher in your local bin directory, a desktop entry, and an icon. S I T then appears in the application menu. The native launcher can reuse an existing backend or start one directly; systemd is not required. Closing a native window also stops a backend that the window started, so wait for recordings and processing jobs to finish first. A manually started backend keeps running independently. The default library is stored below your X D G data directory, normally dot local share slash sit.

06. Connections: managed SSH access
Open Connections from the left sidebar. Enable Reach the AI services through SSH tunnels. Enter the shared SSH host and user. Port twenty-two is normally correct. Leave SSH key empty to use your SSH agent, your normal SSH config, or the default identity files. Otherwise enter the path to a private key. S I T never stores an SSH password. Test SSH connection checks only login and port forwarding permission. A green signed-in result proves that SSH works, but it does not yet start all persistent service tunnels. The application stores connection settings per user in dot local share slash sit slash dot connections dot json with owner-only permissions. For the video, the real hosts and username are redacted; the connection result is genuine.

07. Connections: ASR, speakers, and analysis
Each service has a local port and a remote port. The local port is opened on this computer. The remote port is where the service listens on the remote machine. Every local port must be unique. In this setup, transcription uses local and remote port eight two zero eight. Pyannote speaker recognition uses eight two nine nine. The analysis service uses local and remote port eight one zero zero. Its Advanced section overrides the SSH host because it runs on another machine. The model field must match a model exposed by that server. The transcription API path is slash v one slash audio slash transcriptions, and the diarization path is slash v one slash audio slash diarizations. Advanced settings also support a different remote bind address, API path, per-service SSH host, or a direct HTTP address when tunnels are disabled. The Hugging Face token is only needed by the optional local Pyannote fallback, so a remote-only deployment can leave it unused. Press Set up and test on one service to save the complete form, restart the tunnels, and test that service. Press the main Set up and test button at the bottom to test everything. A healthy remote setup reports that the one-second transcription upload was accepted, Pyannote is running on CUDA, and the configured G P T O S S model is reachable. The diagnostics section also shows tunnel ownership, resolved endpoints, model names, and actionable errors.

08. Choose useful defaults
Open Customization before the first real meeting. Choose a profile for meetings, interviews, lectures, or personal notes, then adjust every default independently. Select the usual project, microphone, output monitor, recording language, live-preview cadence, and expected speaker count. One expected speaker skips speaker separation. Decide whether live transcription and automatic speaker recognition start by default. Reading preferences control the initial transcript view, paragraph grouping, timestamps, and speaker labels. AI analysis defaults control detail, language, comparison with recent meetings, and the sections to request. Privacy preferences choose automatic, local-preferred, or remote-preferred processing. For this remote-only workflow, choose remote processing. Save customizations; they apply to new recordings and newly generated analyses without changing existing results.

09. Create a meeting workspace
Choose New recording. Select an existing project or create a new one, then give the meeting a descriptive name. The preview shows the folder that will be created. Continue to the three-step workspace: Capture, Transcript, and AI analysis. In Capture, choose the spoken language, the microphone for the room track, and the output whose monitor should supply system audio. Pick the output you actually hear. A Bluetooth headset microphone may force the headset into a lower-quality capture profile, so a wired or built-in microphone is often clearer. Enable Live transcript while recording only when a running preview is useful. The final saved recording is transcribed again regardless of that toggle.

10. Record with a live transcript
Press Start recording. The workspace replaces its setup cards with a timer, waveform, recording controls, and the live transcript. The level meter reflects the audio actually reaching S I T. If it remains silent for several seconds, the interface tells you to check the selected microphone. The first live text normally appears after about ten seconds of captured audio plus model processing time. Later updates add new audio while retaining a short context window. The newest provisional segment is highlighted and may change. If processing falls behind, the status shows the delay; slow processing does not intentionally skip segments. Cancel discards the temporary audio and live preview. Stop and save moves the recording into the library and starts the complete transcription workflow. If the recording reaches its time limit, it remains available to save. Do not close the backend while saving or processing is active.

11. Upload and generate a transcript
To process an existing file, choose Upload existing audio instead of recording. S I T accepts common audio formats and video, then uses FFmpeg to normalize the source into a library W A V file. Upload works even when the host has no PulseAudio recorder. After capture or upload, open the Transcript step. Confirm the language and expected number of speakers. Leave the count empty for automatic detection, or use one to skip speaker recognition. Generate transcript sends the audio to the configured remote transcription endpoint. When speaker recognition is enabled, the diarizer labels the timed segments afterward. The progress view reports transcription, diarization, merging, completion, or a real error. In this demonstration, both operations use the working Spark tunnels; the local model is not used. You can rerun speaker recognition later without repeating speech recognition.

12. Review text and speaker names
Open the finished meeting to review timed transcript cues. Selecting a timestamp seeks the audio player to that moment. Choose Edit meeting to correct individual words or labels. Every cue must retain text before it can be saved. Transcript edits mark any existing AI analysis as outdated because the source changed. The Speakers tab groups detected labels and lets you replace them with real names across the whole transcript. Save speaker names once, rather than editing every cue. If separation was incorrect, enter an expected speaker count and choose Recognize speakers again. This replaces speaker labels but keeps the existing speech-recognition text. The Transcript tab can regenerate everything with a different language or speaker count, but that operation replaces the current transcript and derived analysis.

13. Generate AI analysis
Continue to AI analysis after the transcript is ready. Use the saved defaults or expand Adjust this analysis to change detail, output language, instructions, and requested sections for this meeting. The available structured sections include a timeline, decisions, action items, open questions, risks, speaker contributions, and a follow-up draft. Generate AI analysis runs in the background against the configured OpenAI-compatible service. There is no built-in local analysis fallback. The finished brief links important claims back to source timestamps, so selecting a source jumps to the relevant audio. If you edit the transcript afterward, S I T preserves the previous analysis but marks it outdated until you regenerate it.

14. Organize and revisit the library
The Library groups meetings below project folders. Search the current folder, create subfolders, and use each item menu to move, rename, or delete content. A meeting can contain audio, plain transcript text, structured timed segments, Markdown analysis, and structured analysis data. Opening a finished meeting restores its audio player, provenance, transcript, and analysis. Open on disk requires the optional transcriber opener helper; every other library feature works without it. You can always open the data directory manually. Keep backups because this is alpha software and the on-disk layout may still change.

15. Data, privacy, and troubleshooting
By default, the library lives at dot local share slash sit. Transcripts use dot txt files, timed data uses dot meeting dot json, recordings live in an audio subfolder, and analyses use Markdown and JSON sidecars. Temporary work stays under underscore scratch. When remote processing is enabled, audio is sent to the transcription and diarization servers, and transcript text is sent to the analysis server. Use only infrastructure appropriate for that data. Connection secrets stay server-side; the Hugging Face token is write-only in the browser. The FastAPI service has no authentication and intentionally binds to local host by default. Do not expose it publicly. For recording failures, verify that pactl info can see the desktop audio server and that FFmpeg and pactl are installed. For connection failures, test SSH first, then each service. Connection refused usually means the tunnel or service is absent. A four-oh-four points to the API path. A model error means the configured model does not match the server. If a local port is occupied, close the process that owns the old tunnel or assign a different unique local port.

16. Update safely
To update, close S I T and run update dot sh from the checkout. It performs a fast-forward pull, refreshes Python dependencies, rebuilds the native application when Tauri sources changed, and updates an installed desktop entry. Settings, the environment, and library data remain in place. The script refuses to update while the backend is running and refuses to pull across uncommitted changes. Use dash dash no pull when you deliberately want to reinstall the current working tree, and dash dash force build when the native binary must be rebuilt. You now have a remote-only S I T installation with managed SSH tunnels, recording and upload workflows, speaker-aware transcripts, structured AI analysis, and a maintainable local library.
